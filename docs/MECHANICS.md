# MECHANICS — engine rules used by the stat model

Every rule carries a source. Tags:
- **DB** — read from `database.arz` (record + field cited).
- **community** — Crate forum consensus, collected 2026-11-14. Not a dev post. Confirm by swap/dummy test where cheap; the model may use it until a test contradicts it.
- **unverified** — single claim or no source. The model must not silently depend on it: flag it in the tooltip or calibrate it.

Constants and formulas from the DB are added in Phase 3.

**DB names.** The DB keeps legacy field names; the UI tags in `Text_EN` map them (`DamagePoison` = "Acid Damage",
`DamageDurationPoison` = "Poison Damage", `DamageLife` = "Vitality Damage", `DefensePoison` = "Poison & Acid Resistance"):

| DB field family | Game term |
|---|---|
| `offensivePoison*` | Acid |
| `offensiveSlowPoison*` | Poison (DoT) |
| `offensiveLife*` / `offensiveSlowLife*` | Vitality / Vitality Decay |
| `defensivePoison` | Poison & Acid resistance (one resist for both; "Acid RR" = "Poison RR") |
| `defensiveX` < 0 on a debuff | "−X% resistance" (RR category 1) |
| `offensiveTotalResistanceReductionPercent` | "% Reduced target's Resistances" (category 2) |
| `offensiveTotalResistanceReductionAbsolute` | "Reduced target's Resistances" flat (category 3) |
| Intelligence / Dexterity / Strength | Spirit / Cunning / Physique |

## 1. Resistance reduction (RR) — community

Three types, by DB field (DB names above):

| Type | Shown as | DB field | Stacking |
|---|---|---|---|
| 1 | "−X% resistance" | `defensiveX` < 0 on a debuff (`defensiveAllResistance`: the ten base resists, `DefenseAttributeAbs_AllResistance::AddToAccumulator` 0x200C30), its own or its modifiers' | all sources add, unlimited |
| 2 | "X% Reduced target's Resistances" | `offensiveTotalResistanceReductionPercent` | highest only; multiplicative; cannot push a positive resist below 0 |
| 3 | "X Reduced target's Resistances" | `offensiveTotalResistanceReductionAbsolute` | highest only; additive |

Order 1 → 2 → 3, per damage type, starting from the target resist `R`:

```
r1 = R − Σ type1
r2 = r1 > 0 ? r1 × (1 − max type2 / 100) : r1
r3 = r2 − max type3
```

**Scoring an overlap.** Highest-only sources are weighted by uptime (§4): a weaker source counts only while every stronger one is down, i.e. (1 − uptime of stronger) × its value. Only that RR component is reduced; every other stat of the same item counts normally. Never drop an item for one overlapping stat.
Example: awakened Ring of Eternal Rot (`c053_ring.dbr`, proc 18 % type 2) next to Living Bloom (26 % type 2): the ring's 18 % counts for (1 − Bloom uptime); at Bloom uptime 1 it adds 0. Its +2 Vulnerability, +100 % Poison duration and 300 Poison/5 s proc count in full.

Cheap check: none in isolation (the ring's RR comes bundled with other stats). Covered by the Phase 3 ring swap test: model prediction for the whole swap vs the dummy.

## 2. Conversion — community, order and sums from the engine

1. **Same level, additive:** skill transmuter conversion + item skill modifier conversion for the same skill, summed per `in → out` pair.
2. **Global, multiplicative:** gear/devotion conversion (`conversionInType`/`conversionOutType`) applies to the remainder that level 1 left unconverted.
3. Converted damage is never converted again. Consequence: Widow's Bite 25 % Chaos→Vitality + a Vitality→Acid conversion does **not** move the converted Vitality on to Acid; only original Vitality converts. This overrides the guide's "chained conversion" reading.
4. Source types convert in the order they first appear, not Elemental first (**engine**, traced 2026-11-16, next paragraph; the community reading "Elemental before Fire / Cold / Lightning" holds only when the Elemental conversion comes first).
5. **Skill % and sheet % add — engine (Game.dll 1.3.1.2).** The skill's own % (its record, learned modifiers and item skill modifiers) is attached to each damage entry before conversion, the sheet % after it; both are summed into one factor per entry, not multiplied. `Skill::CollectCombatParameters` 0x499570 collects the skill's flat damage and its % through vt+0x3C8 / +0x3D0 (0x496440 → `AddModifierOffensiveDamageAttributes` 0x493480, 0x4964F0 → `AddModifierOffensiveModifierAttributes` 0x4935B0: learned modifiers Skill+0x140, item skill modifiers Skill+0x158), runs `CombatAttributeAccumulator::ModifyDamage` 0x119280 at 0x499A87 (skill %), converts, then collects the character's % (`SkillManager::CollectAvailableOffensiveModifierAttributes` 0x535BC0) and runs `ModifyDamage` again at 0x499DB1. Each run adds its % to the entry (`CombatAttributeAbsDamage::ModifyAbsoluteDamage` 0x1138A0: field +0x2C += %; DoT `ModifyDurationDamage` 0x114300: damage % +0x34, duration % +0x38), and the hit applies damage × (1 + sum / 100) once (`CombatAttributeAbsDamage::Process` 0x113450, +0x2C read at 0x11346E; `CombatAttributeDurDamage::Process` 0x113F30, duration × (1 + % / 100) at 0x114206). This replaces the community reading that skill % multiplies the sheet %.
6. **Conversion dilutes the skill % — engine.** `ConvertCombatAttributes` 0x1197B0 makes the new entry as a copy of the source (vt+0x108), then `ScaleDamage` 0x113930 (× % × 0.01) and `ScaleModifiers` 0x113970 (+0x2C × % × 0.01; DoT 0x1143A0 scales +0x34 only); the source keeps the remainder with both scaled the same way. So a part with share f carries f² of the skill % it had (Elemental targets: (f / 3)² each, 0x7A6FE8 = 1/3). `core/src/score_conversion.cpp` `convert_pairs`.
7. **"Total Damage Modified by x%" multiplies — engine (Game.dll 1.3.1.1, traced 2026-11-18).** `offensiveDamageMultModifier` (skill records, learned modifiers, transmuters, item and set skill modifiers: Bloody Pox's transmuter +60, Worldkeeper's Garden on Grasping Vines +150, Dreeg's Evil Eye's transmuter +160) is a `DamageAttributeAbsMod_DamageMultiplier`. Its `AddModifierToAccumulator` 0x19D200 pushes one `CombatAttribute_DamageMultiplier` entry per record (type 0x3D, value × 0.01) into the same modifier list as the skill %. `ModifyDamage` 0x119280 runs every other modifier first and skips type 0x3D, then runs each multiplier entry on its own: `Execute` 0x117E50 passes max(0, (1 + value) × 100) to the damage entry's `ScaleDamage` (0x113930 direct, 0x114360 DoT) for every damage type (mask 0x8FF6), which multiplies the damage fields by it × 0.01 and leaves the % sum (+0x2C / +0x34) and the DoT duration alone. So damage × Π (1 + mᵢ / 100) × (1 + Σ % / 100): several multipliers compound, and the result multiplies the skill's additive sum. Score: per main skill (`Raw::mult`). A timed proc buff's multiplier (`item_torment` −25 with its item modifiers' own) scales every hit of the player's (main skills, procs, player-scaled pets) while it is up: each buff state of §10 carries it as a factor, a buff left out of the enumeration at its uptime as an expected value. **shortcut:** cast (learned) buffs' and pet modifiers' multipliers are not read.

**Conversion on a toggle or form modifier — community:** a modifier of a toggled skill or form converts all of the character's damage while the skill is on (Fenris 5/5: Werewolf Form Physical and Pierce to Cold), as the toggle's own stats do ([Steam](https://steamcommunity.com/app/219990/discussions/0/583929583674485816/), [Crate forum](https://forums.crateentertainment.com/t/grim-misadventure-186-howling-fenris/139506)). **shortcut:** the engine path is not traced.

**Sum > 100 % — engine:** `ConversionAttributeAccumulator::Weigh` 0x17D520 scales every pair of a source type by 100 / total, per level (the skill's, then the character's); the total includes DoT pairs that `ConvertDamage` then skips, so those keep their weighed share unmoved. The tooltip notes `conversion > 100% (weighed)`.

**Order and chaining — engine (Skill::CollectCombatParameters 0x499E40):** the skill's own conversions first (0x49A3B7), then the character's (0x49A5D7). Entries a conversion creates are flagged (byte +0xF, 0x119E44) and never converted again, in either level, which confirms rule 3: a Chaos→Fire item does nothing on a build whose Chaos all comes from conversions (`tests/test_templates.cpp`). Elemental damage is stored as a third each of Cold / Fire / Lightning (0x7A8010). **Rule 4 — engine:** `ConversionAttributeAccumulator::AddAttribute` 0x17D890 appends one `Data` per new source type and adds a known type's pairs to its `Data`; `Weigh` 0x17D520 only scales; `Apply` 0x17DB20 calls `ConvertDamage` 0x119ED0 once per `Data`, in that order. In each call every pair of the type converts its % of the same entry amount, then the entry keeps the remainder. So an Elemental → Chaos 50% seen before a Fire → Vitality 50% turns a Fire entry into 50 Chaos, 25 Vitality, 25 Fire; the other order gives 50 Vitality, 25 Chaos, 25 Fire. The character level's order is the one `SkillManager::CollectAvailableConversionAttributes` 0x536400 builds (skills, then `Character::GetEquipConversionAttributes`, then vt+0x708; `Skill::CollectCombatParameters` 0x49A588 calls the same three), which the snapshot's `conversions` list keeps. The skill level: `Skill::CollectLocalConversionAttributes` 0x496F00 adds its own profile pairs in field order (0x17DF90), then a tail call that adds the modifiers' (not traced further; the model takes the skill's record, then its modifiers in `modifier_ids` order). `core/src/score.cpp` `convert`, `tests/test_score.cpp`. **shortcut:** a swap appends the candidate's new source types at the end of the list (`model::swap`); the engine's order puts skills before equipment slots, so a swap that adds a source type the skills also carry can be ordered differently.

**Warnings:** a gear conversion is flagged (red line) when its pair is in `conversion_warn`, the build deals the source type itself (≥ 10% of the main skills' damage with the gear conversions taken out: converted damage is not converted again) and the target is not a `[match]` damage type of the preset (no `[match]` types: not one the build already deals).

Cheap check: skill tooltip before/after equipping a conversion item (Phase 3 swap test "conversion item").

**Engine (Game.dll 1.3.1.1, `CombatAttributeAccumulator::ConvertDamage` 0x119ED0), 0.9.5:** a conversion matches every damage entry of its source type (vt+0x10), direct and DoT alike, so Vitality→Acid also moves Vitality Decay to Poison, Physical→X moves Internal Trauma. Physical also matches BasePhysical (type 1); Elemental (58) also matches Cold / Fire / Lightning entries (types 5, 6, 8). A DoT entry (`DamageType` vt+0x20 = 2) is left alone when the target is Pierce, Chaos or Aether (4, 10, 11: no DoT form). Remaining = 100 − Σ % (const 100.0 at 0x7A8134). `core/src/score.cpp` `convert`, `tests/test_effects.cpp` (Sigil of Consumption).

## 3. DoT — community, one part unverified

- **+% of a direct type does not boost its DoT — engine.** `CombatAttributeAccumulator::ModifyDamage` (0x1194C0) runs every modifier's `Execute` on every damage entry. `CombatAttributeAbsDamageMod::Execute` (0x115070) calls only the entry's `ModifyAbsoluteDamage` (vt+0x80), `CombatAttributeDurDamageMod::Execute` (0x1151B0) only `ModifyDurationDamage` (vt+0x88). `CombatAttributeDurDamage` has no `ModifyAbsoluteDamage` of its own (the base one, 0x15880, is empty), and `CombatAttributeAbsDamage` none for duration. So +% Acid never reaches Poison, +% Fire never Burn, and so on for Cold / Frostburn, Lightning / Electrocute, Physical / Internal Trauma, Vitality / Vitality Decay. The sheet agrees: `GetTotalDamageModifierType` (0x11A750) sums by type **and** damage kind, and `lvl16-wp-before-belt` shows Acid +59% next to Poison +68%. Community: [wiki Damage Types](https://grimdawn.fandom.com/wiki/Damage_Types) (+% Cold does not affect Frostburn). What both share: the resist on the target, conversion (a converted type takes its DoT along) and +% All Damage (type 60, spread over both kinds). `tests/test_sanity.cpp` cases 8 / 9.

- Crit is rolled at application; a critical DoT stays critical for its full duration.
- RR is snapshotted at application.
- **unverified** (single forum claim): debuffs that tick every second (Bloody Pox etc.) re-check RR on each tick. The steady-state model assumes all RR is up, so this matters only for the "apply RR first" order, which the model does not score.

## 4. Uptime of conditional effects — design choice

Every conditional effect (proc, pet, temporary buff/debuff, skill with a cooldown) has an `uptime` in [0, 1]. One mechanism for all; no per-item special cases.

- **Default, derived where possible:** `uptime = min(1, proc chance × trigger rate × duration)`. Proc chance and duration come from the DB record; trigger rate from the model (attack/cast rate of the triggering skill). For cooldown skills: `min(1, duration / cooldown)`.
- **On being hit:** trigger rate = threat profile `incoming_hits_per_sec` (per-stage defaults in `docs/PRESETS.md`).
- **Pets:** pets alive × attacks per second per pet, estimated from the pet record (below; experimental).
- **Last-resort fallback `0`** (`docs/PRESETS.md`). Never silent: if any effect on the compared items is at fallback, the tooltip shows `+? unscored: <effect>` next to the total.
- **Override:** per preset and per `[[stage]]`, keyed by the effect's DB record path.
- **Highest-only overlap** (RR types 2 and 3, any other highest-only stat): sort sources by value, strongest first. Source k is the active one with probability `p_k = u_k × Π_{j stronger} (1 − u_j)`; nothing is active with `Π (1 − u_j)`. Score the expected damage over these states, not damage at an averaged RR (type 2 is multiplicative, so the two differ). For two sources the weaker one gets weight `u_weak × (1 − u_strong)`, the rule above. **Design assumption: sources fire independently** (unverified; correlated procs, e.g. two on-hit effects from the same attack, would make this wrong).
- **Shift view** shows each assumed uptime and where it came from (`derived` / `preset` / `default ⚠`).

**Implementation (`core/src/effects.cpp`, 2026-11-14).** Sources and the rate each one gets:
- Learned class skills (not Passive / Modifier / Transmuter / Mastery): the debuff they apply (`buffSkillName` when that record is a debuff, else the skill) with their learned modifiers and item skill modifiers. No `skillCooldownTime` → **design choice:** kept up (uptime 1, e.g. Curse of Frailty `curse1.dbr`); else cast on cooldown (**design choice**), `uptime = min(1, duration / recharge)`, summons/s = 1 / recharge.
- **Recharge** (0.9.7) = `skillCooldownTime` × (1 − CDR) for the character's own skills — learned class skills (cast, own-trigger passives) and devotion powers; item and set skills keep `skillCooldownTime`. **Engine:** `Skill::GetCooldownTime` (0x4917E0) applies CDR unless Skill+0x2F9 or +0x2FC is set. +0x2F9 is `Skill::IsItemSkill` (0x30AD10); its only writers are `SkillManager::AddItemSkills` (0x538BC0, writes 0x0101 to +0x2F9/+0x2FA), `Skill::SetAsItemSkill` / `SetAsItemSkillAuto` (no callers in Game.dll), `SkillManager::CreateSkillBuff` (buff replicas) and `SkillManager::CreateAndLoadSkill` when the manager's +0x412 (`SetAsItemSkills`, no callers) is set. +0x2FC is the record's `potionModifier` (`Skill::LoadResources`) and potion skills (`SetAsPotionSkill`, `Skill_ChargePotion`, `Skill_Potion*`). Devotion powers are in the character's own SkillManager and cast through `SkillAutoCastController::AppraiseAndExecute` (0x523440) → `GetCooldownTime` → `Skill::StartCooldown`, so CDR shortens them. Other callers of `GetCooldownTime`: `StartCooldown`, `UpdateCooldownCharges`, `Skill_OnHitAttackRadius::OnHitActivation`, `Skill_OnHitBuffSelf::Update`, `Skill_Shapeshift::ReceiveActiveUpdate`, `SkillActivatedBuffSelf::ApplyCost`, `HotSlotOptionSkill::GetNumberAvailable`. CDR ≥ 100% → kept up. The cooldown is the skill's plus its learned and item skill modifiers' `skillCooldownTime` (`GetCooldownTime` → `GetSkillModifierData`, above; 0.9.12 for procs and summons, the main-skill path already did). Pets' own skills keep their DB cooldown (the pet's attributes, not the character's: not traced).
- Devotion powers with points: `templateAutoCast` on the skill or its `buffSkillName` record (DB: `tier2_32d_skill.dbr` has only `buffSkillName`; the buff record holds the controller and `skillCooldownTime`).
- Items and sets: `itemSkillName` + `itemSkillAutoController`, level `itemSkillLevelEq` (a number, or `itemLevel/4+1` floored with the **base item's** `itemLevel`; in game: Brigandine Armor `a03_torso001b` (itemLevel 11) "of Balanced Steel" shows Ring of Steel 63 Piercing = level 3 (38) × (Cunning 159 / 245 + 1), screenshot 2026-11-14, one item); set skills at the piece count (`gdc::sets`).
- Proc rate: `per_sec = 1 / (recharge + 1 / (chanceToRun/100 × trigger rate))` (**design choice:** the recharge blocks the next roll). Trigger rate: `AttackEnemy` / `AttackEnemyCrit` → the main skills' attack or cast speed (snapshot `attack_speed` / `cast_speed` read as uses per second: **unverified**, and for spells the engine says otherwise — §5 "Uses per second") × crit chance for crit triggers; `HitByEnemy` → `incoming_hits_per_sec`; `HitByMelee` → that × `melee_share`; `Block` → that × the shield's blocked share (`utility::block_share`); `HitByProjectile` → `incoming_hits_per_sec` × (1 − `melee_share`); `HitByCrit` → `incoming_hits_per_sec` × the enemy's crit chance on you (§9); `LowHealth` → `low_health_per_sec`, the threshold from the controller's `triggerParam`; `OnKill` → `kills_per_sec` (preset, default 0.5, design guess); `OnEquip` → kept up; any other trigger → fallback 0. Passives with their own trigger (DB fields on the skill record): `Skill_PassiveOnLifeBuffSelf` (`lifeMonitorPercent` = the threshold) → `low_health_per_sec` (× the controller's chance if it has one); `Skill_PassiveOnHitBuffSelf` / `…BuffShield` → `onHitActivationChance` × `incoming_hits_per_sec`; `Skill_WPAttack_*` → its chance weight / 100 × the uses per second of the main skills that are weapon pool skills (class `SkillActivatedWeaponPool`: the default attack, Cadence, Savagery). **Engine:** `Skill_WPAttack::GetChanceWeight` 0x5160E0 reads `skillChanceWeight` through the skill's attribute accumulator (with the expansion loaded), so the skill's and its modifiers' weights add (item modifiers such as `shield_d007` +10). `SkillManager::SelectWeaponPoolSkill` 0x5364C0 sums the weights under 100; when that sum is under 100, one entry of 100 or more (rolled by weight) fills the rest; the roll is over max(100, sum). So a weight is a percent chance until the weights pass 100 together, then each counts w / sum and the pool skill itself never comes up (fewer of its own uses, every chance scaled). **shortcut:** a weight of 100 or more is taken as a chance; the caller of the roll is not traced, the class name stands for which uses a pool attack can take. What the effect then does besides damage and RR: §10.
- **One skill granted by several items or sets — engine (traced 2026-11-19):** Dung Divider and Fewmet Grips both grant Noxious Fumes. `SkillManager::AddItemSkills` (0x538520) makes a skill per item and `AddAutoCastController` (0x558C00) a controller per skill, each rolling with its own cooldown (`SkillAutoCastController::AppraiseAndExecute` 0x522D20), so the uses add. Its buff, debuff or DoT on a target is one instance that each use refreshes: one effect at the summed rate, uptime `min(1, rate × duration)`, counted once. Summons stay one per source (each skill holds its own pets). **shortcut:** the higher level stands for both.
- Pets (`spawnObjects`, **experimental estimate**, the tooltip says so). **How many — engine (traced 2026-11-16):** `petLimit`, `spawnObjectsTimeToLive` and `skillCooldownTime` are the skill's plus its learned and item skill modifiers' (`Skill::GetSkillModifierData` 0x49AF90 sums Skill+0x140 and +0x158 through `SkillProfile_Modifiers` 0x54ACF0, profile +0x74 time to live × 1000 at 0x54A8C4, +0x78 `petLimit`; read by `GetPetLimit` 0x493880, `GetSpawnObjectTimeToLive` 0x493660, `GetCooldownTime` 0x4917E0). The last modifier whose vt+0x6F0 is non-zero replaces the time to live: only `Skill_SpawnPetTransmuter` (0x509F40, `modSpawnObjectsTimeToLive[level − 1]`) has one, `Skill_Modifier`'s returns 0. A transmuter's `modSpawnObjects` replaces the pet record, indexed by the summon's level (`Skill::AddModifierPetChanges` 0x494CE0, min(level − 1, size − 1) at 0x50A631). `Skill_TargetedSpawnPet::SpawnPet` 0x50A560 calls `Monster::SetLifetime` 0x37B620 only for a time to live > 0, and every pet record's own `lifeTime` (`Monster::Load` 0x37482B) is 0; past the limit the oldest go (`Skill_SpawnPet::KillExtraPets` 0x509890). So alive = the limit without a time to live — Hellhound, Raven, Briarthorn, Skeletons, and the invincible Blade Spirit (2 / 3 / 4 by level), Squall (3), Celestial Guardian (2), which earlier versions left unscored — else min(limit, summons/s × time to live). Blight Fiend with its transmuter `summon_blightbeast1b` (limit 1 + 2, cooldown 18 − 13 = 5 s, 12 s, `blightbeast_<level>b`) is 12 / 5 = 2.4 pets without CDR. **How often, per pet:** `specialAttack<n>SkillName` at `specialAttack<n>Chance` / max(`specialAttack<n>Delay`, its cooldown) per second (**design reading of the DB fields**), other activated skills with a cooldown once per cooldown, each at most the pet's rate for it; the plain attack (`attackSkillName`, else the pet's own weapon: its `Skill_Passive` skills with flat damage, at 100%) at the pet's rate × (1 − the share of time the others take). The rate: with a live pet of that record in the snapshot (schema 12, `Snapshot::pets`: the adapter walks the player's PetPen) the pet's own `Character::GetAttackSpeed` / `GetSpellCastSpeed` (by the skill's class, §5) × `anim_frame_rate` / `anim_frames` of that skill's hit animation (`SkillActivated::GetHitCallbackPoint` called with the pet; the own-weapon attack takes its SkillManager's `GetDefaultSkillId(0)` skill), the same model the engine uses for the player's spells and that was checked in game for them (§5); not checked for pets. A swap shifts the captured speed by the change of pet bonus %: speed × (1 + (m + Δ) / 100) / (1 + m / 100), m = the pet's `GetTotalCharModifier` 15 / 16 at capture (`CapAttackSpeed` not re-applied). Without a live pet: the record's `characterAttackSpeed` / `characterSpellCastSpeed` × (1 + pet attack / cast speed % + total speed %) from pet bonuses (Class Pet only), read as uses per second (**unverified**: `Character::GetAttackSpeed` 0x692E0 is type 15 × (1 + type 17 `characterBaseAttackSpeed`, × the dual-wield factor at hand state 10) × (1 − 0.01 × the attack-speed slow), clamped by vt+0x688 — `Monster::CapAttackSpeed` 0x37C570: between Monster+0x4EEC % and +0x4EF0 % of type 15 — a speed multiplier, not attacks per second). A preset `pet_attack_rate` > 0 replaces the plain attack's rate. Pet skill levels: `skillName<n>` / `skillLevel<n>`, a number or an equation of `charLevel` (the player's level; `effects::equation`: + − × / ^ and parentheses), plus `SkillSecondary_PetModifier` → `petSkillName` at the modifier's level.
- RR "to all" (`offensiveTotal…`) lands on every type of the `[enemy]` model; `…Elemental…` and `defensiveElementalResistance` on Cold, Fire, Lightning.

## Not modelled
- Devotion refund / "self-support" (e.g. Crane counting its own affinity): irrelevant, the adapter reads the actual devotions.

## 5. Score v1 (`core/src/score.cpp`) — sources per rule

Weights and enemy numbers are design choices in `presets/default.toml` (`docs/PRESETS.md`). Only ratios after / before are shown, so constant factors cancel.

**Damage** per main skill, at its current level (record arrays indexed by level − 1, the last value past the end):
- Flat damage: the skill record's `fields::flat_damage()` fields (re/CombatAttributeType.tsv load fields), average of min/max; a record without any (Skill_AttackBuffRadius) uses its `buffSkillName` record. Plus learned modifiers (`Skill::modifier_ids`, schema 5) and item skill modifiers (DB records), all in the skill's one pool (§2 rule 5): converted with the skill, scaled by the skill % and the sheet %. The log lists each main skill's damage by source (`dmg by source`); the Shift view lists each changed item skill modifier per skill, numbers as the item tooltip (raw × (1 + sheet % / 100 + attribute bonus)), parts the score does not read marked `(not scored)` (`docs/COVERAGE.md`, item skill modifier fields). **unverified:** DoT = per second × `…DurationMin`; `…Chance` < 100 scales by chance.
- Weapon skills (`weaponDamagePct` > 0) add pct × flat damage of equipped items (their getter output; type 1 BasePhysical as Physical) and of passive / toggled skills that are on. **community:** gear flat damage applies to weapon attacks only. **Weapon base damage is never compared** (design choice, 0.9.2): every hand item's own base (`BasePhysical` and the record's `offensiveBase*Min/Max`) is taken out of flat damage and both sides get one shared base = the mean of the two sides' R Hand weapon base, so a weapon swap is scored on its affixes, +skills, procs, conversions, RR and % only. Dual wield: compared against each hand; the L-hand weapon's base is not modeled (noted). Two-handed vs one-hand + off-hand: compared as a pair; item DoT min/max taken as per second (**unverified**).
- Skill % fields attach to the original type before conversion and add to the sheet % (§2 rules 5–6, engine). Conversions: skill level, then the character's on the remainder; converted damage is not converted again (§2, community). Sums over 100% are weighed to 100% and Elemental is a third each Cold / Fire / Lightning (**engine**, §2).
- × the skill's "Total Damage Modified by" multipliers (§2 rule 7), each (1 + m / 100), compounding.
- × `offtarget_weight` (preset, default 1) for a final type that is not one of the preset's `[match] damage` types and that no conversion can turn into one: every type but Bleeding is some record's `conversionInType` in the 1.3.1.1 database and converts into every other, nothing converts into Bleeding, a conversion keeps a part's DoT flag and never moves DoT into Pierce, Chaos or Aether (§2 "Engine"). Main skills, procs and pets alike (design choice, `docs/PRESETS.md`).
- × enemy resist multiplier of the final type: `[enemy]` resist after the RR of both sides (`effects::resist_multipliers`, §1 / §4). Default resists: mean base `defensive<Type>` of the 48 Boss enemy records (DB); difficulty scaling not modelled.
- × (1 + (character % of the final type + the skill's own %, diluted by conversion, §2 rules 5–6) / 100 + attribute bonus); character % from `damage_modifiers` (engine rows; 58 / 60 already spread, not added again).
- Attribute bonus, combatformulas.dbr: physical/pierce `dexterityDV/245`, physical duration (bleed, internal trauma) `/215`, magical `intelligenceDV/215`, magical duration `/200` (DB), **added to** the type's % (one factor `1 + %/100 + attribute`), not multiplied. CDR = the character's total (`utility::cooldown_reduction`, §6). The cooldown is the skill's and its modifiers' / transmuters' `skillCooldownTime` (Dreeg's Evil Eye has none; its transmuter `evileye1b.dbr` 4 s). **Not applied** to item skills and item procs; applied (0.9.7) to devotion procs and learned skills cast on cooldown for their debuff or summons (§4 "Recharge").
- **Charged skills — engine** (`Skill_WeaponPool_ChargedScaling`: Savagery, Righteous Fervor, item skills such as Troll Rage). `IncrementCharge` 0x510100 / `DecrementCharge` 0x5102A0 move the charge count one at a time; the scale is `skillChargeMultipliers[min(charges − 1, last)]` × 0.01 (0x7A6FA0), 1.0 with no array, and the hit's own damage, % and weapon % (0x510E90, 0x510F80, 0x511030) are taken at it; modifiers are not scaled. While charged, the passive collectors (0x5113F0, 0x5116F0, 0x511520) add the skill's and its modifiers' character, defense and % stats to the character. The model scores the hit at the scale of `skillChargeLevel` charges at its level (Savagery 1.0 to level 8, 1.08 from 9, 1.15 from 16, 1.2 from 24) and the charged stats as a buff up 100% of the time while the skill is a main skill. **shortcuts:** sustained combat holds the maximum (the ramp after a pause is not counted); a capture is taken as uncharged unless its passive totals already hold the skill's stats, and one taken charged as at the maximum; the charged `offensiveDamageMultModifier` is not applied to other hits. **Engine:** `SkillManager::GetOffensiveModifierAttributes` 0x52F6E0 leaves out the passive % of the skill being used (same object name), so the skill's own hit takes its own and its modifiers' % and crit damage once, locally at the charge scale, while the charged % reaches every other hit. The model therefore gives the own hit no local % or crit damage on top of the charged buff (or the capture's totals), which hold the same values.
- **Combo charges — engine** (Onslaught). `SkillManager::IncrementComboCharge` 0x53F990 adds one per hit of a skill with `skillComboChargeLevel` (its own and its modifiers'), up to that level. `Skill::CollectComboMultiplier` 0x4993D0: a skill with a cooldown (`GetCooldownTotal` 0x491270 > 0) and damage hits at 100 (0x7A710C) + `GameEngine::GetComboChargeMultiplier` 0x2D8D20 % (`gameengine.dbr` `skillComboChargeMultipliers`), then `Character::SpendComboCharges` 0x603F0 spends the charges unless a roll against skill attribute 4 (`skillComboChargeSpendReduction`) keeps them. The model: charges at a cooldown main skill's use = min(cap, builder uses ÷ cooldown skill uses ÷ (1 − keep)), the multiplier between whole charges interpolated; Shift shows `x1.360 combo (3.00 charges)`. Combo Charge Spend Reduction counts only here, not in Other. **shortcuts:** the per-hit time gate (`GameEngine`+0x1080 / attack speed), the `skillComboChargeDuration` expiry and procs with cooldowns spending charges are not traced; the multiplier is taken on the whole hit (where the engine reads it is not traced).
- **Retaliation in Damage** (`[damage] retaliation = true`, preset `retaliation`; off by default, then retaliation stays an `[other]` key). `CombatManager::Retaliation` 0x11FBB0: the character's retaliation flat (items, worn set tiers, skills up: passives always, buffs and toggles at their uptime; a chance counts as an expected value) × (1 + retaliation % of the final type), after the conversions of each buff state (a conversion item or buff moves the retaliation of that side and state only); no offensive %, attribute bonus or crit. Per second = `incoming_hits_per_sec` × that × enemy resist × type weight, added to Damage like a proc. **% Retaliation Added to Attack** (`retaliationDamagePct`, `Skill::CollectCombatParameters` 0x499570): the skill's own retaliation and the character's × pct / 100 join that skill's hit (main skills and procs). **shortcuts:** retaliation DoT, crowd control, % of current life and `retaliationDamageMultModifier` are not counted; buff damage multipliers do not apply; which incoming hits trigger it (melee / ranged / spells) is not traced; pet retaliation is skipped.
- **Procs and pets** (`extra_damage`): every non-learned effect of §4 with flat damage (its record or its `buffSkillName` record) or `weaponDamagePct` (× the weapon and gear flat damage, as for a weapon skill) adds `per_sec × one use`. A `Skill_WPAttack_*` replaces a use of a weapon pool skill among the main skills: it counts whole here, and its chance × those main skills' damage per second comes off (`replaced weapon pool uses` in Shift), so the main skills keep their per-use meaning. Only the uses it fires on come off: with a cooldown that is `min(chance, per_sec / weapon pool uses per second)`. Every rate tied to the player's attacks (on-attack and on-crit procs, weapon pool attacks) and the DoT cap below are worked out per buff state, at its own attack / cast speed and crit chance: `per_sec × r(state) / r(snapshot)` with `r = 1 / (recharge + 1 / (chance × trigger rate))`, so two items granting one proc keep their sum. Cadence (`Skill_WeaponPool_ChargedFinale`) hits `skillChargeLevel` (2) plain weapon hits, then its own: a pool attack can take a plain hit, never the finale ([Grim Dawn wiki](https://grimdawn.fandom.com/wiki/Masteries), [Steam](https://steamcommunity.com/app/219990/discussions/0/133258593400269678/)), so its use is the cycle's average and only the plain hits' share is replaced. **shortcut:** the cycle applies in scoring, not in the auto skill pick. A proc's DoT from one source does not stack on a target ([Steam](https://steamcommunity.com/app/219990/discussions/0/451850849184341319/)): past one use per DoT duration (× the duration modifier) the uses add no DoT (factor `min(1, 1 / (per_sec × seconds))`); main skills are not capped (**shortcut**). A pool attack weaker than the Cadence or Savagery hit it replaces costs damage (Damage is floored at 1% of the main skills' part). There is no separate "build relevance" factor: a proc of a type the build has no % for is small because it gets no % bonus, not because it is zeroed. A proc's use goes through the character's conversions, % per type, attribute factor, enemy resist, hit and crit like a main skill; a `Class Pet`'s use (**experimental**) is its attack's flat damage (plus its weapon × `weaponDamagePct`) × per type (1 + (pet bonus % of that type, all-damage and Elemental, + the pet's own passives' %) / 100 + its Cunning / Spirit bonus by the player's combatformulas) × enemy resist × its expected hit at its OA against the enemy DA. Pet bonuses: the equipped items' (and affixes' / components') `petBonusName` records, learned skills' and devotions' `petBonusName` (own or on the `buffSkillName` record; timed buffs and sets left out, **shortcut**). The pet's Cunning / Spirit / OA: its `characterAttributeEquations` record's equations of the player's level, plus pet bonus flat and %. **shortcut:** the player's formulas taken for pets, no pet crit damage, DoT duration or conversions. With no attack of the player's own (a pure summoner, every state with pet or proc damage) Damage is the pets' and procs' damage per second alone. A `PetPlayerScaling` summon (Living Bloom / Blossom, totems, mines; `effects::summoned`) is scored like a proc (the character's conversions, %, attributes, hit, crit; label `(player-scaled pet)`): **engine** — its seven `ContributeMisc*` (0x3C8840..0x3C88B0) jump to `Character::ContributeMisc*`, skipping `Pet::ContributeMisc*` (0x3C7C10..), which add `GameEngine::ContributePetBonus*`, so no pet bonus; `Skill::CollectCombatParameters` (0x499E40) swaps such a caster for its owner when the owner is a Player. Item skills without a controller count as cast on cooldown (design choice). To put them on the main skills' scale: main / s = Σ cooldown skills (one use / cooldown) + the others sharing the casts by weight at the snapshot's attack / cast speed (read as uses per second: **unverified**) — design choice. **Damage is a function of one side** (0.9.2): D(side) = G + k × extra/s, G = exp(Σ weight × ln skill damage), k = √(G ÷ main/s of the before state × the same of the after state) (one constant for both sides, so a swap and its reverse stay reciprocal; 1.0.1 and earlier used G × (1 + extra/s ÷ main/s) let a main skill with a small weight but a large share of main/s move the procs-and-pets part when nothing proc-related changed), each term from that side's own sheet, and the shown ratio is D(after) / D(before). So a swap and its reverse are exact reciprocals: |(1 + x)(1 + y) − 1| < 0.5% is a test (`tests/test_symmetry.cpp`, every fixture pair and synthetic ring / off-hand / weapon / two-hander / requirement cases). 0.9.1 took the arithmetic mean of after/before ratios with the before side's weights and the before side's main/s, which made both directions positive (tome ↔ shield: +6.3% / +8.7%). No attack / cast speed in the snapshot → procs and pets not scored, noted.
- **Attack vs cast speed — engine:** `Player::CalculateSkillDps` (0x3E06D0) takes the speed by skill class: `SkillActivatedWeapon` / `WeaponPool` → `CalculateAttackSpeed`, `Skill_AttackRadiusSpin` → `GetAttackSpeed`, `SkillActivatedSpell` / `SkillActivatedBuffSelf` → `GetSpellCastSpeed` (0x693A0). A class outside those branches (`SkillSecondary_*`, unknown) falls back to attack speed with weapon damage, else cast speed. - **Uses per second — engine (traced 2026-11-15; used from 0.9.8 for the speed cap, the on-attack / on-cast proc rates and the cast share of non-cooldown main skills):** the model reads `cast_speed` (`Character::GetSpellCastSpeed` 0x693A0 = char attribute 16 (SpellCastSpeed) × (1 − 0.01 × combat type 18, the cast-speed slow on the character), then vfunc +0x680; base 1.25 = `characterSpellCastSpeed` of `malepc01.dbr`) as casts per second. `Player::CalculateSkillDps` does not: for `SkillActivatedSpell` / `SkillActivatedBuffSelf` it stores `SkillAttackInfo+0x30` = cast speed and `+0x2C` = cast speed × `frameRate` / `frameCount` of the skill's hit animation (0x3E0CD2..0x3E0CFD; both from `SkillActivated::GetHitCallbackPoint` 0x51A310, vtable +0x6E0, which asks the character's animation object (vtable 0x6D4D48, slot +0x80 = 0x20B40) for the animation holding the `RightHandHit` / `LeftHandHit` / `Both` callback and returns `GraphicsAnim::GetLength` (Engine 0x977A0, +0xC8) and `GetFrameRate` (0x977C0, +0xCC)). So casts per second = 1.25 × (1 + cast speed %) only for an animation exactly one second long. The animation per skill and its frames are not known offline (resolved at run time by the skill's animation type, Skill+0x5C4, and the character's animation set). Weapon skills (`SkillActivatedWeapon` / `WeaponPool`) take `Player::CalculateAttackSpeed(true)` × 0.01 ÷ a vfunc +0x50 of the weapon's object (1.0 without one) instead, and `Skill_AttackRadiusSpin` takes `GetAttackSpeed`; neither is traced further. Without a capture (weapon skills, schema < 10) procs on attack and the speed cap still rest on `cast_speed` / `attack_speed` being uses per second (**unverified**, off by frameRate / frameCount). Since 0.9.8 the adapter reads them for every learned `SkillActivatedSpell` / `SkillActivatedBuffSelf` (snapshot schema 10). **Verified in game (2026-11-15):** winterpoison, cast speed 1.375, every captured skill 19 frames @ 30 → 2.17/s; Devouring Swarm held 10 s from full energy = 22 casts. Nothing in it is a time: both speeds are multipliers on animation playback, and uses per second = speed × frame rate / frames of the skill's hit animation, as `CalculateSkillDps` does for spells (verified above). - Auto skills: learned `records/skills/playerclass*` skills of class `Skill_Attack*`, `Skill_BuffAttackRadiusToggled` or a `SkillActivatedWeaponPool` subclass (class tree) with damage, top `auto_skills` by points, weighted by points (a skill's points include its learned modifiers' and transmuter's: Bloody Pox 1 + Black Death 12 = 13; `skill_weights = "points"` the same); all on cooldown → default weapon attack fills in (`filler_weight`). **Survivability:** EHP = Life / damage taken per incoming attack, through the pipeline of §9 (dodge / deflect, enemy OA vs DA, block, enemy damage reduction, resists, armor per region), × the threshold curves. Resists: R_t = min(uncapped − `resist_reduction`, max) (sheet values, `model::sheet`); `resist_reduction` (a preset design choice: incoming enemy RR) lowers the 9 base resists only. Base absorption: every armor entry carries `GameEngine::GetArmorDefensiveAbsorption` (engine, traced: `DefenseAttribute_BaseProtectionAbsorption::LoadFromTable` 0x204420 copies GameEngine+0x1328, which `GameEngine::LoadFromDatabase` 0x2C8830 loads from `gameengine.dbr armorDefensiveAbsorption` = 70; `AddToAccumulator` 0x204BF0 builds one entry per piece with armor > 0; `GetTotalDefenseType(39)` 0x11A880 averages the positive entries), × (1 + absorption modifier %). Procs add three more factors and buff the totals (§10). Not scored: DoT vs hit split, stage 5 of §9, stage 8 outside procs.

**Other:** 1 + Σ weight × value over the preset's `[other]` keys whose `when` holds + `default` × Σ unlisted stats / 100 (`gdc::utility`, §6). Weights are design choices (`docs/PRESETS.md` "Other"). Granted skills (items, sets) are listed "+? unscored" only when neither the stat model (ungated passives) nor §4 / §10 gives them a value; set fields outside `gdc::fields` always are.

**Components:** base item = item stats − relic stats − augment stats (per accumulator row; absorption left alone), minus the components' flat damage from their DB records (matched by value). Slot fit: the record's `amulet` / `ring` / `medal` / `head` / `chest` / `shoulders` / `hands` / `legs` / `feet` / `waist` flag (DB: present on all 491 ItemRelic / ItemEnchantment records). Completion bonuses are not moved (noted).

## 6. Skill levels, buffs and utility stats (2026-11-14)

**+skills** (`model::swap`). A skill's stats at the old and new level come from its record's per-level arrays, so every mapped field moves with the level: damage, RR, % bonuses, resists, flat stats of passives and auras. Main skills and their modifiers are scored at the new level in Damage; RR through `gdc::effects` (§4).
- **All and Elemental resistance** on set tiers, buffs, passives and devotions (`defensiveAllResistance`, `defensiveElementalResistance`) go through the stat model, spread as the engine does (`DefenseAttributeAbs_AllResistance::AddToAccumulator` 0x200C30: the ten base resists; `…ElementalResistance` 0x200A70: Fire, Cold, Lightning), so they meet the resist cap like an item's resists.
- **+mastery** goes to every skill with that `mastery_id` (`SetMasteryAugment` 0x5373D0). **The mastery bar itself does not rise** — store 20261114-172933-952 records 1 → 2 (Occultist +1 item): every Occultist skill's augmented level rose by 1, `_classtraining_class03.dbr` stayed 0, and the mastery record has no `skillUltimateLevel` (DB). Community agrees: item bonuses to a mastery do not raise its bar ([Steam: GD mechanics, "+skills"](https://steamcommunity.com/sharedfiles/filedetails/?id=1855311027)). Evidence is from one level-50 mastery only.
- **0-point skills:** +levels to a skill with no points do nothing (`GetCurrentLevel` 0x4909C0 returns 0 for an unlearned skill). Score 0; the tooltip lists them grey `X +n (unused, 0 points)`.
- **Timed buffs you cast** (0.9.3; `model::buff_timing`): a class skill (`records/skills/playerclass*`) whose stats record (its `buffSkillName` record or its own) is a `SkillBuff_Passive` / `Skill_BuffSelfDuration` with a `skillActiveDuration` (DB classes and fields). The consumables the skill list also holds (50 records at level 1 on winterpoison: resist potions with `skillActiveDuration` 900 and no recharge) are not: 0.9.2 counted them as permanent buffs, which put +30 on every resist of both sides. **Uptime** = min(1, `skillActiveDuration` / (`skillCooldownTime` × (1 − CDR))) at the skill's current rank, CDR = the character's total (0.9.4, snapshot schema 9 `skill_attributes`: `SkillManager::CollectAvailableSkillAttributes` 0x535BE0 — equipped items, learned skills incl. devotions, running buffs, item skills — as `SkillAttributeAccumulator::GetValue` 0x51F1A0 gives it without the chance parts, value + |value| × modifier / 100); older snapshots: the equipped items' sum. The formula is the user's rule ("recast on cooldown", preset `recast_buffs`); that CDR shortens this recharge is not traced in the engine. Blood of Dreeg rank 3: 60 s / (12 s × 0.88) → 100%. **Normalization** (`model::expected`): before scoring, a learned timed buff that is up (snapshot `buff_active`, schema 8) is taken out of the totals with its modifiers, an active proc self buff (§10) likewise; on a normalized snapshot a swap never adds a timed buff's level change to the totals (`InactiveLevel::timed`), on a raw one with the buff running it takes the buff out as it was and puts it back as it is after the swap. **States** (`score::compare`): each side's buffs that are neither always up nor never (learned ones and procs' timed self buffs) split it into on / off states; every term (Damage, Survivability, Other) is computed on the real totals of each state (the buff at that side's rank and modifiers) and mixed by the states' probabilities, buffs taken as independent — so a resist cap or a threshold applies per state, not to an averaged sheet. Up to 4 buffs per side are enumerated (16 states), those with the largest uptime × (1 − uptime); the rest stay on the totals × uptime. A buff at 100% is simply on. Each term is mixed on its own and geometrically (0.9.4): ln X = Σ p_state × ln X_state for X = Damage, Survivability, Other, so total = D^a × S^b × O^c still holds, the parts add up exactly and the reverse swap is exactly reciprocal (symmetry test: 1708 pairs, worst |(1+x)(1+y) − 1| = 9e-8). Buffs that add nothing to the totals and absorb nothing are not enumerated (they cannot change either side). **Learned passives with their own trigger** (`Skill_PassiveOnLifeBuffSelf`, `Skill_PassiveOnHitBuffSelf`, e.g. Fighting Spirit `fightingspirit1.dbr`: 24% when hit) are self buffs at the uptime their trigger gives, as an item's proc (§10), not cast on cooldown. Toggles and auras have no duration: they are in the engine's totals, always on. `buff_mode = "live"`: learned timed buffs as the snapshot caught them (on = 100%, off = 0%), procs unchanged. Snapshots before schema 8: state not known, nothing removed, nothing enumerated. **Not in the states:** a buff's own `skillCooldownReduction` / `skillManaCostReduction` (29 / 3 buff records in the DB; skill attributes, which the model's totals do not re-derive): the Shift view lists them per buff as "(not modeled)" (0.9.5), and a buff caught running keeps its part in the snapshot's CDR total (CollectAvailableSkillAttributes counts running buffs; `model::expected` does not take it out). The Shift buff block also lists every char / defense stat of the buff that no sheet line shows (speeds, max speeds, avoidance, slow resist, ...: `tooltip::buff_lines`).

## 7. Requirements — engine (Game.dll 1.3.1.1 disassembly)

- Raw values: the item's virtual getters (`ItemEquipment::GetLevel/Strength/Dexterity/IntelligenceRequirement`, vt+0x528..0x540); each is the max of the item, its relic (+0x1558) and its augment (+0x1560) (0x343AB0, 0x343BD0). The printed value comes from the `itemcostformulas_*` equations at item load; we read the result, not the equations.
- `Item::AreRequirementsMet` (0x326930): `level >= E(L, LevelReqReduction (54))` or L = 0.
- `ItemEquipment::AreRequirementsMet` (0x343C30): that, then per Physique / Cunning / Spirit (char attribute 1 / 2 / 3): `total >= E(R, red)` or R = 0, with `red` = the totals of the item's three reduction types (+0xDF8.. per attribute, the first always, the others when non-zero; e.g. Weapon / Melee / Shield / Armor / Jewelry `*ReqReduction`) + `GlobalReqReduction` (53) when > 0.
- `E(r, x) = trunc(r − r·x·0.01 + 0.5)` (float; 0.01 at 0x7A7FC8, 0.5 at 0x7A8024).
- Tooltip: the candidate's check uses the engine's call (`met`) only when it ran against the snapshot's own level, difficulty and Physique / Cunning / Spirit totals (`requirements.met_at`, `requirements::engine_met`); otherwise the formula on the snapshot decides. The adapter keeps hovered and bag items in a pool and rescoring them after a level-up used the old flag (0.9.8: "can't equip yet" + "the engine disagrees" on an equippable medal, `tests/test_requirements.cpp`). With a fresh flag core's formula only names what is missing and a mismatch is a model warning. Not covered: a requirement reduction (types 53 / 54, the item's `*ReqReduction`) that changes while level and attributes stay. After a swap, the formula runs on the predicted sheet for every other equipped item that met its requirements before; one that fails is shown red and taken off (scored as removed), which can break another (at most 4 rounds).
- Unverified: whether the engine checks the candidate with the old item still worn (assumed: yes, the current sheet).

**Enemy resistance reduction** (`[survival] resist_reduction`, default `"auto"`). What a monster takes off a player's resist is `defensive<Type>` < 0 (and `defensiveElementalResistance` for Cold / Fire / Lightning) on its debuff records (classes `SkillBuff_Debuf`, `SkillBuff_DebufTrap`, `SkillBuff_Contageous`, `SkillBuff_DebufFreeze`), category 1 of §1; no skill of these 2559 monsters has an `offensive*ResistanceReduction*` field. Per level: for each of the nine base resists, the monsters whose skills (record or `buffSkillName`, at `skillLevel<n>`) lower it and the median amount among them; `rr_share` = the mean share over the nine resists, `rr` = the mean amount weighted by those shares. Result (1.3.1.2): 2.6% of the monsters lower a given resist by 7.5 (level 1) to 8.2 (50) points, 3.1% by 11.2 at 60–70, 3.6% by 17.6 from 80 on; 103 to 183 records, all but one Champion or Hero. **Bosses** (`boss_rr`, `boss_rr_share`): the same over the 485 Quest (408), Boss (48: 19 + 29 Nemesis) and SuperBoss (29) records: 7.1% lower a given resist by 12.1 up to level 50, 7.3% by 18.2 at 70, 7.3% by 25.3 from 75 on (charLevel equations up to `charLevel × 1.1 + 2`). The same on every difficulty (the paks carry no such field; the records have no per-difficulty skill data). The score mixes three states per base resist: `(1 − b)(1 − rr_share) + b(1 − boss_rr_share)` at f(resist), `(1 − b) rr_share` at f(resist − rr), `b boss_rr_share` at f(resist − boss_rr), with `b` = `[survival] boss_share` (default 0.15; 1.3.1.2 has 485 of 3044 records = 0.159; a design choice: bosses are fought longer than one record suggests, raise it for boss stages), in the damage taken and in the `resist` threshold (geometric there), so losing overcap costs a few hundredths of a percent per point while a point under the cap costs in full. A number in the preset (any `[[stage]]`) replaces the mix by an always-on reduction from `resist_reduction_from` on (game difficulty; below it the mix stays), e.g. the guide's 25 at `plague-garden` 94+ (Shattered Realm and Ascendant altars are not in the table). Records are not weighted by how often they spawn. `tests/test_regress.cpp`, `tests/test_score.cpp`.

**Difficulty lookahead** (`[survival] difficulty_lookahead`, default on). On Normal and Elite (Veteran included) every state above is scored twice: as now for `1 − t`, and for `t` with the next difficulty's extra penalty taken off as well (§8, `re/PlayerResistByDifficulty.tsv`: Normal → Elite 25 on Pierce / Cold / Fire / Poison / Lightning, Elite → Ultimate 25 on all nine), so overcap up to that penalty counts before the switch. `t` ramps linearly from 0 to 1 over levels 65–75 on Normal and 84–94 on Elite and stays 1 past them. **Design choice:** the database has no level range per difficulty (`records/proxies/limit_area*.dbr` clamp the spawns of 10 pools only); 75 and 94 are the switches of the Plague Garden guide's level plan. The cap is 80 on every difficulty (`playerDefenseCap`), so only the penalty moves. Ultimate and Ascendant have nothing ahead (Ascendant uses Ultimate's balance level). `tests/test_score.cpp`.

**Crit for my damage** (§5): the same `expected_hit` against the table's DA. PTH past 135 only adds 1.5× crits; +crit damage adds to every tier above 1.0.

**Contributions** (`score::Result::contributions`, Shift line `top:`): every factor of Survivability has its own ln ratio (Life, DA, dodge / deflect, block, enemy damage reduction, each threshold; the `resist` threshold per resist, joined with that resist's damage part); the damage-taken sum is split over the damage types, Damage over the main skills and procs, Other over its keys, each in proportion to its linear change. × the term's exponent × 100 = points of the total; the parts add up to ln(1 + total).

**Shift sheet lines** take their points from the comparison the lines themselves show: the items as hovered, components included (`Slot::hovered`; when that total differs from the headline, which compares both items without components, the heading states it: `sheet as hovered, components included: +2.4% [points of it]`). 0.9.8 put the headline's points on them: "Life 4093->4002 (-91) [+1.1]" was Life 3957 → 4002 without the worn medal's Corpse Dust. A part that still moves against its line is printed on its own (`Life: other effects [+1.1]`), never on the line. `tests/test_regress.cpp`, `tests/test_tooltip.cpp`.

## 10. Procs beyond damage and RR: crowd control and self buffs (0.9.1) — design, DB fields

**Choice:** a proc's self buff is not scored as a thing of its own. Its stats × uptime are added to the character's totals (`model::buffed`, the same `derive` a swap uses) and the whole score runs on that sheet, so a resist buff meets the resist cap, armor goes through the armor equation, DA through the hit table, OA / damage % through Damage — no second copy of any formula. Uptime is §4's: `min(1, per_sec × skillActiveDuration)`, `per_sec = 1 / (cooldown + 1 / (chance × trigger rate))`, so recharge and duration both cap it; preset `[uptime]` overrides it. Since 0.9.3 a timed proc buff below 100% is a buff state like the learned ones (§6): the score runs with it on and with it off and mixes the two by uptime (low-health buffs by their weight below); its % and flat absorption follow the same state. What the totals cannot hold becomes a Survivability factor:
- **Crowd control** on enemies (`offensive{Stun,Freeze,Knockdown,Fear,Confusion,Petrify,Sleep,Trap,Convert}Min/Max/Chance`, re/CombatAttributeType.tsv 42..53; seconds × chance, the longest kind per proc, procs combined as independent): damage × (1 − `cc_share` × uptime). `cc_share` (preset, default 0.1, design guess) = share of incoming damage from enemies the CC really stops; enemy CC resists and the proc's radius are not read.
- **Absorption** of a timed buff: × (1 − u × `damageAbsorptionPercent`/100) × (1 − u × min(1, `damageAbsorption` / enemy hit)). **Heals and absorb shields** (`skillLifePercent` × Life + `skillLifeBonus`; `damageAbsorption` of a buff without a duration, once per use): life per second against the life lost per second (`incoming_hits_per_sec` × enemy hit × damage taken per attack), at most 90% of it. **unverified:** flat absorption per hit vs pool, where the engine applies either (§9 stage 8), the shields' `…DamageQualifier` types (ignored).
- Self buff = record class `Skill_BuffSelfDuration`, `Skill_BuffSelfShield`, `Skill_GiveBonus`, `Skill_PassiveOnLifeBuffSelf`, `Skill_PassiveOnHitBuffSelf`, `Skill_PassiveOnHitBuffShield`, or a `buffSkillName` record of class `SkillBuff_Passive`, and their subclasses in the engine's class tree (0.9.9: `Skill_BuffSelfImmobilize` Blade Barrier is a timed `Skill_BuffSelfDuration`; `Skill_PassiveOnCritBuffSelf` is an on-hit buff). **Audit (0.9.9, all ten masteries' buff skills against the DB):** `Skill_PassiveOnCritBuffSelf` (Inquisitor and Berserker `passive02`) is triggered by the owner's crits (**engine:** `Character::AttackTarget` → `SkillManager::OnCriticalAttack` 0x535900 → vtable +0x1F8 `IsSkillOnCritActive` 0x5021E0 → +0x1A8 `OnHitActivation`): rate = attacks × crit chance × `onHitActivationChance`. `Skill_BuffRadiusToggled` auras keep their flat damage on the `buffSkillName` record when it is a `SkillBuff_Passive` (Presence of Virtue, Aura of Conviction, Elemental Infusion, Blast Shield, Nature's Blessing, Amatok's Pact; Aura of Censure's is a `SkillBuff_Debuf`, left out). `Skill_ProjectileModifier` (Blackwater's RR) counts through its parent only, not as a skill of its own. Applies to item, set and devotion effects alike. **Low-health buffs** are up when needed: uptime = min(1, threshold / 100) × min(1, per_sec / `low_health_per_sec`) — the threshold (`lifeMonitorPercent` / the controller's `triggerParam`) is the share of a fight's danger they cover (design choice). **Shortcuts:** buff fields outside `gdc::fields` (mana cost, racial) add nothing; a buff's retaliation counts only under `[damage] retaliation` (§5). A buff up at snapshot time is removed first (§6 buff normalization).
- Parts in `top:`: `Proc crowd control`, `Proc absorb / heal`; buff stats show under the part they move. Tests: `tests/test_sanity.cpp` "granted …".
